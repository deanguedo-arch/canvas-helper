# Course standards promotion: first operational slice

Implemented September 30, 2026. Default nonblocking. No existing course has been adopted or regenerated by this change.

## Executable artifacts

- `config/course-standards/v1.json`: Dean's authorized outreach baseline, five-stage lesson blueprint, requirements, exemplar lineage and component version. Grade 10 is the authoring reading target; 120 words is the initial paragraph ceiling, a routine implementation default rather than a certified reading-level measurement.
- `config/course-standards/promotion-queue.json`: durable opportunities, decisions, immutable release snapshots and scoped bindings. The real registry starts empty; tests do not seed fabricated decisions.
- `scripts/lib/course-standards.ts`: idempotent capture, exclusive writer lock, atomic saves, external-write comparison, optimistic revision checks and scope resolution.
- `scripts/lib/standard-lesson.ts`: actual editable HTML renderer, dark contents sidebar styling, Next step links, saved reasoning, independent-check feedback, structured-content and canonical-HTML acceptance checks.
- `scripts/lib/codex-course.ts`: existing `course:create` workflow consumes the resolved standard. It pins the complete snapshot in `meta/course-standard.json`, records its fingerprint in the manifest and supplies a draft authoring blueprint. Draft slots require completion. It never changes an existing course.
- `app/studio/src/components/StandardsReview.tsx` and `app/server/routes/course-standards.ts`: queue visibility on startup/focus/review capture, explicit Universal/family/course-specific/defer/skip controls, conflict errors and serialized server writes.

## Automatic checkpoints and inheritance

Studio review acceptance captures only the project and a hashed review-item/sent identity. It does not persist teacher notes, excerpts, answers, screenshots or student data. Accepting a course edit is not approving a reusable standard.

After the existing authoring deviation gate passes, the shared export preflight captures a curriculum-entry hash. Brightspace, SCORM, single HTML, Google-hosted and Apps Script exports use that preflight. This is an export-preflight opportunity, not evidence of successful packaging or a live LMS upload. Identical checkpoints deduplicate. Capture failures warn and leave the original workflow running.

Studio presents a persistent pending/deferred count and refreshes on focus. English/Social build commands and the Studio release command print the current standard and pending count. Project authoring context and generated prompt packs include canonical guidance. AGENTS directs new repository chats to the context command and pinned snapshot. Existing owning factories retain their own renderers; this slice does not convert their shells. Arbitrary chats outside these entrypoints cannot be guaranteed a proactive notification. No scheduler, PR bot or third-party notification was installed.

Direct fresh starters resolve course binding, then family binding, then universal, then v1. Each accepted release retains its parent, source checkpoint/fingerprint, scope and timestamp. Existing snapshots remain pinned; adoption into a current course is deliberate work. Course-specific bindings are available to that project's authoring context without changing its saved content.

## Review semantics and boundaries

This deliberately narrow UI promotes two numeric fields—target reading grade (8–12) and maximum words per lesson paragraph (40–250)—and one deterministic teaching rule: `modeledReasoningBeforeGuided: true`. It displays the precise value, an example and impact before scope selection. A capture is an opportunity, not general semantic inference from teacher feedback. For the teaching rule, the system proposes the exact rule from a checked structural observation and Dean's explicit worked/guided expectation; the teacher selects its approval scope. Opportunities without this evidence retain the numeric selector. Family inference uses the declared course code/title, with folder-slug fallback; unsupported families are explicitly `general`.

Universal affects future unbound starters. Family affects the displayed family. Course-specific affects that project. Defer remains visible; Skip remains in durable history. A stale revision, invalid value, finalized candidate, active writer lock or detected outside edit fails safely. No arbitrary text or executable code can be promoted through the endpoint. Broader pedagogical/component changes require a separate reviewable implementation and version release; this slice does not claim its three typed fields capture all teaching knowledge.

## Validation and operation

`npm run course:create -- --slug <slug> --title "<title>" --course-code "Biology 30" --summary "<summary>"` creates the inherited editable draft. Complete the canonical HTML authoring slots and source/outcome mapping before release. The structured `Lesson` renderer API can take complete student-free lesson content through the same creator; the synthetic Biology fixture demonstrates this without copying or reprompting an example course.

`npm run standards:check -- --project <slug>` checks the canonical entry against its pinned snapshot. It checks version identity, five stages, paragraph ceiling, activity purpose/instructions, outcomes/sources/exemplar presence, draft slots and an independent answer key with explanatory feedback. It returns `unadopted` for a legacy course without a pin. Export emits these findings as nonblocking warnings. Existing release/readiness/deviation gates remain authoritative.

Presence checks do not certify source accuracy, Alberta outcome alignment, actual reading level, subject appropriateness or teaching quality. The synthetic fixture explicitly labels its outcome alignment as requiring teacher confirmation. Mobile/resume/SCORM behavior is covered by the representative browser proof and existing bridge tests, not by a claim of live Brightspace verification.

Final verification: 75 focused tests passed (standards, course creation/Edit/Undo, Archive, continuity, security, SCORM export and codec); Studio production build passed. Browser proof exercised five decisions/reload with mocked mutation responses and real read-only queue/origin checks. Actual decision/persistence tests used temporary registries. Fresh synthetic Biology passed corrective feedback, 390px layout, local reload and SCORM restore in a fresh browser context with a mock LMS. Repository TypeScript has pre-existing failures elsewhere; no changed-file errors were reported.

The test fixture is `scripts/tests/fixtures/standards-biology.ts`; the final rendered proof and screenshots are task-owned, outside `projects/`. Main course sources, SCORM packages, Archive selections and all historical recovery work remain untouched. No commits, pushes, deployments or physical retirement occurred.

## Teaching-feedback inheritance proof

The additional typed rule addresses the explicit need to model reasoning before students attempt guided practice. At a review/export checkpoint, a pinned five-stage direct lesson with worked-before-guided structure but no explicit action-and-why list receives a proposal. It contains a source fingerprint, observed structure, explicit expectation, before/after blueprint, rationale and illustrative Biology reasoning. No source excerpts, review notes or student responses are stored. This observation does not claim the existing explanation lacks pedagogical quality.

Explicit Universal/family/course-specific approval creates a version with `context → explanation → worked → modeled-reasoning → guided → independent-check`, `outreach-modeled-reasoning-v2` blueprint identity and retained proposal provenance. The actual starter creates modeled-reasoning authoring slots; complete lesson generation requires at least two nonempty action/why steps. The renderer places that component before guided practice, supplies the Next step links and keeps its text in canonical editable HTML. The canonical validator checks the version, sequence and action/why components. Earlier pinned v1 HTML and snapshots remain unchanged and validate against v1. This is a stricter modeled component, not an automatic rewrite of historical projects.

Invalid false/unsupported rule values, missing or changed proposal signatures, altered curriculum fingerprints, changed baseline ordering, inconsistent enabled-rule/blueprint combinations and already-required scopes are rejected. Defer and Skip do not create a release and stay nonblocking. Approval does not judge reasoning correctness, subject accuracy or instructional quality; those remain teacher review. Arbitrary source/factory formats are not inferred or migrated by this feature.

`scripts/tests/pedagogy-promotion.test.ts` proves real HTTP capture → scoped approval → fresh course creation and validation, including universal/family/course-specific behavior and existing-version preservation. The Studio browser proof forwarded requests to these real handlers in a task-owned registry, exercising actual persistence rather than mocked mutation logic. It approved Family, deferred and skipped synthetic candidates, reloaded, generated a fresh student-free Biology lesson, checked component order/links/canonical HTML and 390px layout, and compared the earlier HTML/pin byte-for-byte. The real queue remains revision 0 with no candidates/releases; no real teaching proposal was approved.
