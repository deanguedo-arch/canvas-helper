# Course standards consolidation and retirement plan

Status: proposed migration and promotion workflow, not implemented. Only the separate project organization registry and Archived/Restore UI are approved for implementation now. Archive means catalog organization; it does not change readiness, canonical ownership, physical paths, or release state.

## Outcome and existing foundation

A fresh Brightspace import should inherit a named, versioned course standard without Dean repeatedly supplying an example and requesting visual repairs. Preserve valuable decisions as executable defaults, reference examples, provenance and checks rather than requiring entire historical projects to remain in the teaching catalog. Models do not passively learn every repository file or permanently change their weights from course edits; future sessions need explicit retrieval and deterministic tooling.

Already present, from targeted code inspection:

- `course:create`, English/Social owning factories and the new-course editability/readiness contract. Extend these entrypoints rather than introduce a competing scaffold or handcraft new roots.
- `scripts/lib/intelligence.ts`, `scripts/lib/pattern-bank.ts`, `scripts/lib/memory-ledger.ts`, collection/apply adapters and prompt-pack generation. Repository `config/intelligence.json` selects `apply`; effective flags can still differ by project/env/CLI. Patterns and ranked memory can influence generated prompt packs. Ledger derivation's default `approved=true` is an implementation signal, not proof Dean approved a universal teaching standard.
- `config/authoring-preferences.json`: hidden source support, approved CALM benchmark, structural require/forbid rules and paragraph-run threshold. `scripts/lib/intelligence/apply/deviation-gate.ts` supports explicit acceptance flags and preference updates. `scripts/lib/exports/shared.ts::runExportAuthoringPreflight` already calls that gate.
- Review Sets persist draft/sent/accepted/reopened and resolved state in browser-local storage. `app/server/routes/session-log.ts` saves project session checkpoints; those logs capture layout/source/resume context, not a teacher-approved universal standards queue.
- `.github/workflows/new-course-readiness.yml` and `studio-direct-editing.yml` run existing readiness/release checks. `app/server/studio-server.ts` has project-discovery/HMR signaling. These are feasible extension points, not an existing cross-chat promotion notification system.

## Operational standard, versioned together

Proposed `config/course-standards/v1/manifest.json` pins shell, lesson blueprint, import mapping, component library, asset catalog and acceptance-profile versions/hashes. Each new project's metadata records `standardId`, `standardVersion`, source lineage, and explicit course overrides. Initial v1 is a reviewed extraction; do not assume the newest file or every exemplar detail is universal.

1. Extract shared shell/navigation, typography, responsive layout, reader/tool controls, progress/save accessibility and evidence handling into intentional `scripts/lib/course-standards/v1/` modules. Exported packages receive self-contained copies; never depend on a historical project path at runtime.
2. Create a structured lesson blueprint: outcomes/prerequisites -> explanation with source-grounded visuals -> worked example/model -> meaningful guided practice -> feedback/correction -> transfer/check -> evidence/reflection where justified. Include optional branches, workload and prerequisite-vocabulary rules. Allow discipline profiles rather than impose a single interaction on every subject.
3. Define Brightspace source mapping from item IDs/order/resources into blueprint slots, with provenance, exclusions, unresolved mappings and source-authority decisions. Preserve original curriculum fidelity; unresolved mappings remain blocked. No student records enter this pipeline.
4. Extend the existing intake/factory/scaffold commands to resolve the pinned default profile automatically. Build the teacher-editable HTML and versioned shell together, preserve stable IDs/state and Studio ownership. Require a compact override only when a course intentionally differs. Record explicit upgrade/adoption; never silently rebuild old courses under a changed standard.
5. Enforce structural checks (complete surface inventory, durable edit keys, links/assets, source mapping, accessible controls); visual checks (representative desktop/mobile screenshots, navigation/reader/dialog states against approved baselines); content checks (outcome/source coverage, vocabulary before assessment, workable examples and feedback, paragraph runs and missing evidence); engineering checks (save/state migrations, reversible Studio edit lifecycle, SCORM packaging). Automated checks support teacher review, not proof of pedagogical quality.

## System-triggered promotion across sessions (future work)

The teacher must not remember to ask. Implement a durable, student-free `config/course-standards/promotion-queue.json`, independent of browser state and ignored caches. Each candidate includes ID/deduplication fingerprint; originating project, source commit/build and resolved review item; before/after rule and representative example; rationale; affected disciplines/component/checks; universal/family/course scope; proposed artifact diff; risk; state and decision provenance.

- **Capture trigger:** after an explicitly accepted Review Set resolution or course correction, a server endpoint persists a candidate/event before browser state disappears. Acceptance means a reviewed course improvement, not automatic universal promotion. Build/apply adapters record relevant changed-area evidence after successful application; do not capture teacher/student saved answers.
- **Catch-up trigger:** export preflight and release runner inspect the actual source diff since the last reviewed source fingerprint, enqueue missed eligible changes idempotently, and report pending candidates. Extend existing hooks, not a new separate export workflow. PR CI can emit an artifact/job summary with pending counts and candidate IDs. A Git diff alone cannot infer teacher approval; queue as unreviewed.
- **Cross-chat surfacing:** Studio startup/focus and after review/export load pending server queue state and show a plain “Review proposed standards” action. Course-context/scaffold/import/release CLI entrypoints emit the pending batch in structured output. A future AGENTS/startup retrieval instruction supplements those deterministic hooks; instructions alone are insufficient. Existing HMR can refresh the UI after queue changes. No currently inspected capability guarantees an unsolicited prompt in every arbitrary Codex chat; automatic chat/desktop notifications require a separately wired supported trigger or an expressly authorized automation. Do not claim these notifications operational now.
- **Teacher decision:** batch a small set of reusable rule + example + impact diffs; offer Universal, Course family, Keep course-specific, Defer to named milestone, or Skip with reason. Persist skip/defer and deduplicate repeat suggestions. Default pending promotion is informational and must not block release. Any stricter release policy needs separate explicit agreement; propose a release flag/report warning and a visible “Defer and continue” action.
- **Accepted promotion:** version the actual shell/blueprint/components/mapping/checks with a reviewed change; validate a fresh representative lesson plus affected existing regression; record source lineage, release notes and superseded decisions. New courses inherit the approved version; existing courses opt into a planned migration with override/state compatibility checks. No accepted rule remains only in prose or memory rankings.
