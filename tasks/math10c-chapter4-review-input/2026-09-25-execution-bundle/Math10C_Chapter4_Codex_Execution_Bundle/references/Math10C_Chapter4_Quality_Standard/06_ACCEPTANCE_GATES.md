# Reusable generation acceptance gates

**Status:** Proposed acceptance specifications. The included audit observations are not passes of these future implementation gates. Automated checks establish only their bounded behaviour; teacher and learner judgments are separate.

Use failure examples as real learner inputs, not substituted canonical answers. Keep expected mathematical outcomes independently reviewed. A DOM class, answer-bank count or passing build cannot establish a teaching capability.

## Required reviewer walkthroughs

Walk through a prepared learner, a learner making a specific conceptual error, a learner with correct mathematics in different notation, a learner needing only entry assistance, and a learner who exhausts the task's credit checks. Inspect the problem before consulting the builder's success summary.

For each, record the original response, actual feedback, available next action and evidence change. Where the course cannot assess a response reliably, preserve it and describe the limitation. Do not fabricate a confident misconception diagnosis.

## Completion rule for the generation workflow

A chapter draft cannot receive internal quality parity merely because all feature-presence tests pass. Relevant hard correctness and learner-dead-end failures must be fixed. Teaching/source review findings must be resolved or explicitly reported, not averaged away by a high visual score. Set a bounded internal correction budget; when it is exhausted, return the exact remaining failures rather than asking Dean to rediscover them.

This gate moves routine rework into the development cycle. It does not eliminate mathematical review, initial calibration, sampled teacher review or separate release acceptance.
